CH 07 · WRITEUP

hv-drop

2026-07-14 · hypervisor, kernel driver, windows

hv-drop is the substrate underneath the real work: a small, signed kernel driver that Windows 11 will load as a demand-start service on a fresh test box, plus the batch file that gets a box into a state where it will let you.

It's not a hypervisor in the "run guest operating systems" sense. It's the piece that comes first — the driver, the boot config, the certificates. What runs on top of it is what I actually care about.

Why do this by hand

You can go download a driver-signing service, upload a .sys file, get a cert back, install it. That's how the polished projects look. It's also how you learn nothing. I wanted to know what bcdedit /set testsigning on was actually toggling, what certutil -addstore TrustedPublisher puts into the store, and why sc create ... type= kernel works at all.

What the deploy actually does

The install.bat is a one-shot. On a fresh Windows 11 test box, running as Administrator, it:

  1. Copies hyperv.sys, the loader, and the test-sign cert to C:\hv-drop\. Fixed path, no ambiguity.
  2. Installs the cert into both Root and TrustedPublisher. Kernel loader wants both.
  3. Enables test-signing via bcdedit, then turns off automatic restart on failure. That last one matters: if the driver bugchecks, I want to read the code, not blink at a reboot loop.
  4. Registers the driver as a demand-start kernel service. Does not start it. That happens after the machine reboots so testsigning is in effect.

The BSOD I actually wanted

The interesting failure mode isn't a load-time reject — it's a late crash from something I did in DriverEntry. I left auto-reboot off precisely so I could stand there, read PAGE_FAULT_IN_NONPAGED_AREA, and know I dereferenced a UNICODE_STRING before initialising it. The first three iterations were exactly that.

What's next

The substrate exists. The real project sits on top of it and stays private for now.
